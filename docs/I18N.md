# Internationalization (i18n)

> **English** · [简体中文](I18N.zh-CN.md)

FreeRemoteDesk ships two languages — Simplified Chinese (`zh-CN`) and English
(`en`) — and a language picker in both UIs. There is **no third-party i18n
library**: the whole mechanism is ~100 lines per app.

The language for a first visit is **detected from the browser/OS locale**: a
`zh*` locale lands in Chinese, anything else in English. An explicit choice from
the picker is stored and always wins thereafter.

## What's localized where

| Surface | Where the strings live | Picker |
|---|---|---|
| PWA (browser viewer + landing page) | `pwa/src/i18n/{en,zh-CN}.ts` | `pwa/src/i18n/LanguageSwitch.tsx`, on the connect screen, the setup screen, and the landing footer |
| Agent window (Tauri WebView) | `agent/src/i18n/{en,zh-CN}.ts` | `agent/src/i18n/LanguageSwitch.tsx`, in Settings and under the main screen |
| Agent tray menu + Rust fallbacks | `agent/src-tauri/src/i18n.rs` | none — follows the saved language, applied at next launch |
| Docs | `*.zh-CN.md` next to each `*.md` | language bar at the top of every doc |

Not localized, on purpose: wire-protocol field and message names, WebRTC session
states reported by the browser (e.g. `connecting`), device brand names
(`iPhone`, `iPad`, `Mac`), console/`log` output, raw diagnostic error text (some
of it is produced by the browser — "Permission denied" — and is matched on, so
translating it would change behaviour), and the `signaling/` Worker, which has no
user-facing text. The agent's error screen therefore localizes only its heading
and shows the raw message underneath.

## Why the module is duplicated

`pwa/src/i18n/` and `agent/src/i18n/` are near-identical copies, and that is
deliberate. Vercel builds `pwa/` as its own project with a plain `npm install`
(see [`DEPLOY.md`](DEPLOY.md) and `pwa/vercel.json`), so it cannot resolve a
`workspace:*` dependency. Sharing the module through the pnpm workspace would
break the deploy. The module is small enough that two copies cost less than that
risk.

The two copies have drifted in one spot: the agent's `LanguageSwitch` accepts an
`onChange` callback so the choice can be mirrored into the Rust config; the PWA
has no Rust side and omits it.

## How a translation is looked up

```
t(key, vars?)            → string   translate, substituting {name} placeholders
rich(text)               → ReactNode  render **bold** / *italic* / `code`
useI18n()                → { t, lang, setLang }   subscribes to language changes
```

- `en.ts` is the source of truth for the key set: `MessageKey = keyof typeof en`.
- `zh-CN.ts` is typed `Record<MessageKey, string>`, so **a missing translation is
  a `tsc` error, not a silent English fallback**. `pnpm typecheck` catches it.
- Values may embed a tiny inline markup — `**bold**`, `*italic*`, `` `code` `` —
  which `rich()` turns into elements. This keeps a translated sentence in one
  piece instead of splitting it into one key per fragment. Render those strings
  through `rich()`, not directly.
- Components subscribe with `useI18n()`; non-React modules (`pwa/src/savedHosts.ts`)
  import `t` directly for one-shot lookups.

## Persistence

| | PWA | Agent |
|---|---|---|
| Where | `localStorage["lang"]` | `localStorage["lang"]` **and** `language` in the agent config |
| Authoritative on load | `localStorage` | the config file — the agent adopts it during bootstrap, because that value is what the tray menu was built from |
| First run | detected locale | detected locale, then written back to the config on bootstrap |

Changing the language in the agent also calls the `set_language` Tauri command,
which writes `language` into the config JSON. The Rust side reads it for the tray
menu and for the one Rust-generated user-visible string (`"Unknown device"`).
Rust cannot see the browser locale, so its own fallback is a fixed `"zh-CN"`
(`config.rs::DEFAULT_LANGUAGE`) — but the WebView persists the detected language
on bootstrap, so the only window where they disagree is the very first launch
before the window opens. The tray menu is built once at startup, so **a language
change reaches the tray on the next launch, not immediately.**

`<html lang>` is kept in step by `applyDocumentLang()`, called from `main.tsx` in
both apps.

## Adding a string

1. Add the key to `en.ts`.
2. Add the same key to `zh-CN.ts` (the typecheck will tell you if you forget).
3. Use `t("your.key")` — or `rich(t("your.key"))` if the value contains markup.

Both dictionaries are grouped by screen with `// ---------- Section ----------`
comments; keep that grouping.

## Adding a language

1. Copy `en.ts` to e.g. `ja.ts` and translate the values.
2. Register it in `i18n/index.ts` — extend `Lang`, add it to `DICTS`, add an entry
   to `LANGS` (the label is the language's own endonym, e.g. `日本語`).
3. Type it as `Record<MessageKey, string>` so missing keys fail the typecheck.
4. For the Rust side, add the tag to `SUPPORTED_LANGUAGES` in
   `agent/src-tauri/src/config.rs` and a branch in `i18n.rs::tr`.

Nothing else needs touching: `readInitialLang()` validates stored values against
the known set, so an unrecognised tag falls back to the default rather than
breaking the UI.

## Docs

Every Markdown file has a Simplified Chinese sibling named `<name>.zh-CN.md`
(`README.md` → `README.zh-CN.md`, `docs/DEPLOY.md` → `docs/DEPLOY.zh-CN.md`). Each
file carries a one-line language bar under its H1 linking to its counterpart, and
relative links inside a translated doc point at the translated variant.

**The English files remain canonical.** `AGENTS.md` in particular is written to be
pasted into an AI coding agent, and the install prompt quoted in the README is
English — keep both usable as-is when editing. This doc set defines the
convention: when you add a new doc, add its `.zh-CN.md` sibling and both language
bars.
