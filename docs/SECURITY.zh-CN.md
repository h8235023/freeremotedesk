# 安全模型

> [English](SECURITY.md) · **简体中文**

## 威胁模型

我们假设：
- 信令服务器是**诚实但好奇的（honest-but-curious）**（它由我们运行，但设计必须在它被攻陷时依然站得住）。
- 网络完全对抗（Dolev-Yao）—— 每个数据包都可能被观察、丢弃或篡改。
- 用户已配对的设备是可信的。如果你的笔记本电脑被盗且处于解锁状态，攻击者就拥有了你的远程桌面。这一边界我们依赖操作系统级别的设备认证（passkey + 生物识别）来守住。

**文件传输（在初始威胁模型之后加入）。** 已配对的客户端可以向主机的 `下载/FreeRemoteDesk/`
写入文件，主机也可以把文件推给客户端（浏览器按普通下载处理）。这**不是新的权限等级** ——
已配对的客户端本来就拥有主机的完整键鼠控制权，写文件严格弱于它已经能做的事。现有措施针对的
是「别弄坏主机」，而不是授权：

| 措施 | 原因 |
|---|---|
| 文件名在主机侧净化 | 文件名来自对端。只取 basename（杜绝路径穿越），替换禁止字符与 Unicode 双向控制符，裁剪结尾的点号/空格，转义 Windows 保留设备名，按字符边界截断。 |
| 写入限定在单一目录 | 任何调用方提供的路径都不会进入文件系统。 |
| 不覆盖 | 绝不覆盖已存在的文件，而是追加 ` (1)` 后缀。 |
| 声明的大小是硬上限 | 对端发送的字节超过其声明时立即中止，因此无法塞满磁盘。 |
| `.part` + 重命名 | 中断的传输不会留下一个看起来完整、实际被截断的文件。 |
| 可配置上限 | `max_transfer_bytes`（默认 512 MiB）。由 Rust 强制执行；客户端自己的检查只是为了快速报错。 |

浏览器侧的接收路径会在下载开始前把整个文件放进内存（浏览器没有 File System Access API
就无法流式落盘），所以那个方向有自己更低的上限。

## 保证

| 属性 | 实现方式 |
|---|---|
| 机密性（视频、输入） | WebRTC DTLS-SRTP —— 强制启用，端到端。信令服务器能看到 SDP，但看不到密钥或内容。 |
| 完整性 | 每个数据包都有 DTLS-SRTP MAC。 |
| 真实性 | 配对时的 WebAuthn 仪式把设备凭据绑定到特定的主机 agent 上。每个会话都是一次全新的 WebAuthn 断言质询。 |
| 抗重放 | 每次会话初始化中都带有 nonce；每次连接都会协商短期 WebRTC 会话密钥。 |
| 信令服务器被攻陷 | 攻击者可以对配对发起 DoS，但无法解密会话、伪造新的配对（WebAuthn 会阻止他们），也无法冒充已配对的设备。 |

## 我们**不**保证什么

- **端点被攻陷。** 如果你的主机被拿下，我们无能为力。操作系统级别的屏幕捕获就是本产品的全部。
- **元数据隐私。** 信令服务器能看到哪些 agent ID 在何时与哪些 client ID 通信。它永远看不到内容。
- **匿名性。** ICE 收集期间 IP 是可见的（这对 P2P 是必需的）。如果你需要向对端隐藏自己的家庭 IP，请使用仅 TURN 模式（可在 Phase 4 中实现）。

## 认证流程（细节）

### 配对时（一次性）

1. 主机 agent 在安装时生成 ed25519 密钥对。公钥在本地注册。
2. 主机 agent 向信令请求配对码。得到 `x7k2q9`，有效期 60 秒。*（这 60 秒的有效期**并未在代码中强制执行**——见[速率限制](#速率限制)。）*
3. 用户把配对码读给 PWA 客户端（或扫描二维码）。
4. PWA 以配对码 + PWA 的 WebAuthn 凭据创建选项 POST `pair.claim`。
5. 信令完成匹配，在两者之间打开一条双向通道。
6. WebAuthn 仪式：用户浏览器弹出提示要求生物识别/PIN，创建绑定到 `freeremotedesk.com`（rpId）的凭据。
7. PWA 通过信令把凭据 ID + attestation 发送给 agent。
8. Agent 验证 attestation，存储凭据 ID。
9. 双方现在可以协商 WebRTC。

### 会话时（之后每次连接）

1. PWA 向信令出示 `credentialId`。
2. 信令把质询转发给主机 agent（连接时该 agent 必须在线）。
3. 主机 agent 生成一个每会话 nonce，通过信令发送给 PWA。
4. PWA 执行 WebAuthn `get()` —— 用户生物识别解锁凭据，对 nonce 签名。
5. 断言发送至信令，再转发给 agent。
6. Agent 依据已存储的凭据公钥验证断言。
7. 继续进行 WebRTC 协商。

## 速率限制

### 已实现的部分

对 `/ws/` 的 WebSocket 升级会经过一个滑动窗口计数器，保存在 Worker 的模块作用域内存里
（`signaling/src/index.ts`），以 `CF-Connecting-IP` 为键：

| 限制 | 默认值 | 可通过什么调整 |
|---|---|---|
| 每 IP | 30 次 / 分钟 | `MAX_WS_PER_MIN_PER_IP` |
| 全局 | 600 次 / 分钟 | `MAX_WS_PER_MIN` |

超出时返回 `429` 并带 `Retry-After`。猜测配对码每次尝试都要开一个 WebSocket，所以这是
限流器唯一能咬住的地方。

**它刻意没有做成 Durable Object。** 按 IP 建 DO 会让拥有大量 IP 的攻击者在「付账单的那个
账号」上创建无上限的 DO 实例 —— 把请求配额问题变成更糟的问题 —— 而且会迫使每一个已有
部署再做一次 migration。`MAX_TRACKED`（5000 个键）给这个 map 封了顶，避免限流器本身
成为内存耗尽的途径。

### 诚实地说，它不是什么

- **不是安全边界。** Cloudflare 在同一机房内和跨机房会跑很多 isolate，所以分布式攻击者的
  实际额度是「限制 × isolate 数」，而且 isolate 回收时计数器就没了。它是一个尽力而为的滥用
  刹车，限制的是别人烧你免费额度的速度。
- **保护配对码的并不是它。** 默认 16 位、31 字符字母表下空间约 79 bit，这个量级下在线猜测
  根本不是威胁。限流真正起作用的是**下限**（6 位约 30 bit）——这也是 `pairing.rs` 里写明
  「优先使用默认值」的真正原因。
- **不能替代有效期。** 泄露的配对码只要房间里的对端还连着就一直有效 —— 仍然没有 TTL，
  也没有一次性消费（见 [`PROTOCOL.zh-CN.md`](PROTOCOL.zh-CN.md#此前记载于此的特性)）。

### 此前记载于此、至今仍未实现的

以下几条在 fork 之前就被声称存在，但代码里依然没有：

- **配对码猜测**：每 IP 每分钟 5 次；全局每分钟 1000 次（任意 IP）—— 已被上面的真实限制
  取代，但那个是尽力而为的。
- **会话初始化**：每凭据每小时 60 次（防止失控循环）—— 不存在这样的计数。
- **WebSocket 连接**：每 IP 20 个并发 —— 只限制了速率，没限制并发；Durable Object 限制的
  是**房间**最多两个对端。
- `env.RATE_LIMITER` 绑定（Cloudflare Rate Limiting API）—— 没有使用；它需要付费套餐，
  而 Worker 内的限流器完全不需要任何绑定。
